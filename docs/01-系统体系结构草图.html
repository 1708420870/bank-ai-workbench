01结论与设计立场

本项目的技术实质不是"做一个客服问答机器人"，而是在一个不可信的信任边界上安全搬运数据。所有架构复杂度都来自这一个事实，客服业务只是它的第一个负载。

斯坦福案例给出了这个判断的原始证据：一家受联邦银行监管、曾有合规处罚记录的大型零售银行，其技术政策禁止在企业防火墙之外使用任何软件或硬件，但业务又要求部署基于云的 AI 虚拟助手。团队没有去推翻政策，而是设计了四件套——出域清洗、合成数据替换、意图处理外置、返回时重装——把"云计算能力"和"客户数据"在空间上彻底解耦。结果是渠道成本降至最低服务等级、呼叫处理时长下降 48–72 小时。①

本方案把这四件套工程化为一条可测试、可审计、可回滚的链路，并补充案例中没有展开的三件事：裁决权归属、工具权限边界、失败时的默认行为。

三条不可让渡的原则

其一，裁决权恒定在内网。模型与智能体只产出"候选建议"（candidate suggestion），不产出业务结论。是否展示、如何分流、工单状态、任何业务动作，由内网规则引擎与授权人员决定。这条原则一旦松动，整个架构的合规基础就没了。

其二，脱敏不可交给生成式模型。模型会漏识别、会误改写、会被提示注入操纵。字段识别、令牌化、出域扫描、映射复原必须由独立的内网确定性服务执行，与智能体完全解耦。

其三，一切失败默认关闭。校验不过、超时、会话不匹配、模型返回非法结构——默认动作是转人工，不是"尽力而为地继续"。安全边界不因可用性压力而让步。

02必须先澄清的架构悖论

这是立项前必须由银行书面确认的第一件事

"内网与外网严格物理隔离"与"实时调用外网大模型 / 外网通过 MCP 访问内网工具"不能同时无条件成立。如果两张网络之间不存在任何跨域通道，实时 API 调用在物理上不可能发生，MCP 也只是一个应用层协议，不会自动打通网络。

把这件事前置澄清，不是技术洁癖，而是因为后续所有工作量都取决于这个答案。三种可能形态对应三套完全不同的实现：

形态网络特征能否实时外呼对本项目的影响
A 严格物理气隙 内外网无任何在线链路，仅人工审批的介质交换 不能 智能体只能连接内网可达且获批的模型端点；外网 WorkBuddy 退化为离线草稿包处理。客服链路的"外置意图"环节需改为批处理。
B 物理分区＋受控跨域交换
本方案采用		 独立网络，边界经银行批准的安全交换平台/DMZ 网关做白名单交换，不提供任意路由 可以，但仅限批准字段、方向、接口 可完整实现四段式护盾与 MCP 受控访问，保留可审计的数据路径。代价是必须通过网络安全、数据合规两道审批。
C 内网 Agent ＋ 内网模型 Agent 与模型端点均在内网，外网不进入链路 不需要 合规压力最小，但放弃外部模型能力，且需另行核算 GPU。可作为 B 被否决时的降级基线。
措辞建议

正式技术文档中应使用准确表述："内外网独立部署、网络分区隔离，跨域数据通过银行批准的安全交换设施受控传递"。只有在两网之间完全没有任何数据通道时，才使用"严格物理气隙"这一表述。用词失准会在安全评审阶段直接触发返工。

03三区总体结构

三区的划分依据不是"部署位置"，而是该区域内允许存在什么形态的数据、以及谁拥有裁决权。这是本架构最核心的一条：区域是按数据权限定义的，不是按机房位置定义的。

各区的不变量（Invariant）

下面四条是架构级约束，任何实现都必须满足；后续所有代码、测试、验收都围绕它们展开：

区域允许存在的数据绝对不能出现的东西
内网 D0 原始客户数据、令牌映射表、权威规则库、密钥、完整审计日志、员工身份 无（内网是信任根）
DMZ 过境中的 D2 级令牌化载荷；临时缓存必须带 TTL 与自动清理 客户原始数据、令牌映射表、完整业务库、可长期驻留的任何业务数据
外网 D2/D3 级脱敏上下文、任务元数据（编号、状态、耗时、模型版本）、办公产物 原始身份字段、令牌映射、可复原的客户档案、内网数据库的任意直连路径

关于"为什么外网服务器不需要 GPU"

这一点在评审中经常被误解，需要写明：外网节点的职责是接收脱敏任务、管理会话队列、组装提示词、调用托管 Agent API、校验响应、记录审计元数据。模型推理发生在托管服务或外部模型平台，不在该节点上。因此外网节点的配置指标是 CPU、内存、网络带宽与高可用，不是 GPU。把模型权重算进 Agent 节点是常见的资源规划错误。

05两条核心链路

任务书把两条链路混在一起叙述，容易在实现时把"客服主链路"和"办公辅助链路"写成一条。它们是两条独立的跨域路径，字段白名单与审批口径都不同，必须分开建模。

链路 A　客服辅助主链路

  • 触发：客服员工提交咨询
  • 跨域次数：1 次（去）＋1 次（回）
  • 外发内容：令牌化上下文 + 规则摘要
  • 回传内容：候选建议 + 风险标记
  • 终态：员工确认后入工单
  • 模型归属：牛马仕 → 模型连接器 → 内网/外模型端点

链路 B　科技人员办公辅助链路

  • 触发：科技人员或工作台请求生成材料
  • 跨域次数：1 次（出域生成）
  • 外发内容：已批准的工单摘要（D3 级）
  • 回传内容：交接卡、待办、简报文本
  • 终态：人工审核后归档
  • 模型归属：外网任务服务 → WorkBuddy Managed Agent

链路 A：客服辅助主链路（12 步）

逐步标注了执行区域与该步的失败动作。后者是设计的一部分，不是异常处理补丁。

  1. 身份识别内网
    SSO/MFA 认证，按岗位授予客服 / 主管 / 审核员权限。失败 → 拒绝进入，不降级为匿名。
  2. 任务创建内网
    员工输入咨询或选择已授权的客户/交易；生成全局唯一 request_id 与 session_id，绑定操作者身份。失败 → 不生成请求，不进入后续环节。
  3. 最小取数内网
    按最小权限读取必要字段。原始字段不拼接进任何外部请求，也不交给未授权 Agent。
  4. 字段识别与令牌化内网 · 独立服务
    结构化字段走规则/正则确定性替换；非结构化文本用经评估的 NER 辅助。生成 NAME_001、CARD_001 等不可逆外部标识，映射加密写入内网存储。失败 → 阻断出域，不允许"跳过脱敏继续"。
  5. 规则摘要提取内网
    提取允许外发的意图类别、规则编号与摘要。禁止整库知识、完整流水、内部敏感策略外发。
  6. 出域扫描内网 → DMZ
    白名单字段校验 + 原值残留扫描 + 敏感实体扫描 + 附件检查。任何命中原始敏感值 → 阻断并记录审计事件。
  7. Agent 编排内网
    牛马仕接收最小化上下文，按任务配置选择已登记模型端点，通过白名单 MCP 工具调用必要服务。不允许出域时只能走内网端点。
  8. 模型调用内网 / 经 DMZ 至外网
    调用已获批端点，返回结构化候选建议、依据摘要、待确认事项、风险标记。端点不可达或未获批 → 停止调用，转人工或内网降级。
  9. 响应校验内网 + 外网两侧
    Schema、长度、字段白名单、敏感内容、request_id、Agent/模型版本五项校验。非法响应直接丢弃。
  10. 规则裁决内网 · 规则引擎
    本地规则引擎重新决定是否可展示建议、是否必须转人工。外部建议与内网规则冲突时以内网规则为准。
  11. 字段复原内网 · 复原服务
    仅在 request_id ≡ session_id ≡ 当前员工身份三者匹配，且响应签名、来源、版本均通过时，按当前会话回填最少字段。复原后的文本不再外发。
  12. 人工确认内网
    员工采纳 / 修改 / 转人工 / 驳回；系统记录确认结果，形成可追溯审计记录。
最关键的一句

第 10 步是整条链路的重心：外部大模型给出的是"建议"，不是"决定"。任何把这个判断权交给模型输出的实现——哪怕只是"高置信度时自动回复"——都会直接导致验收不通过。

链路 B：办公辅助链路（8 步）

  1. 发起外网
    获授权的科技人员或工作台在 WorkBuddy Enterprise 发起任务。
  2. MCP 连接外网 → DMZ
    经 MCP Connector 连接 DMZ 的 MCP 网关，完成认证、工具授权、限流、审计。
  3. 白名单转发DMZ → 内网
    网关仅把允许的请求转发给内网 Facade；Facade 不是数据库直连代理。
  4. 只读取数内网
    可读规则目录、规则元数据、已审批的脱敏规则摘要、合成案例、聚合指标。
  5. 草稿提交内网
    可提交新 Skill / Workflow / Agent 配置 / 规则变更草稿，进入待审批区，不直接改变生产。
  6. 沙箱验证内网
    用合成数据或批准样例在隔离环境跑自动化测试。
  7. 三方审批内网
    业务负责人确认语义，科技确认权限与数据流向，安全确认日志与工具范围。
  8. 版本化发布内网
    签名、依赖扫描、权限检查、回归测试后按变更流程发布；保留前一版本与回滚路径。

06四段式数据护盾

这是斯坦福案例的直接工程化。四个环节各自解决一个独立问题，缺一环则整条链路失效：

环节解决的问题实现方式失败动作
① 出域清洗 原始标识符不得跨边界 结构化字段直接取白名单；非结构化文本用正则、词典与经验证的 NER 辅助 识别置信度低、出现未知敏感字段 → 阻断出域
② 令牌替换 不能靠"看不出来"来保护，需要可复原的确定性映射 真实值替换为 NAME_001 类外部标识，映射加密存储于内网 映射写入失败 → 终止流程，不发送任何内容
③ 意图外置 语义理解必须用外部算力，但不能带走事实 外网模型只做意图分类、归纳、方案建议；输入是抽象意图 + 令牌化上下文 模型返回未知意图码 → 拒绝自动处理，转人工
④ 复原重装 员工需要看到真实信息才能工作 内网按会话、请求编号、操作者三元匹配后回填最少字段 三者任一不匹配、会话过期、签名异常 → 拒绝复原

出域载荷的真实形态

下面这个结构是链路 A 第 6 步之后实际穿过边界的对象。它没有金额、没有商户、没有时间戳——这不是遗漏，是刻意的：不要让模型"回答得更像真实客服"而多发送一个字节。

字段级别说明
request_idD3全局唯一，用于幂等、关联与重放检测
schema_versionD3契约版本，不匹配则拒收
intent_hintD3枚举值，例 SUSPECTED_UNAUTHORIZED
sanitized_contextD2仅含令牌的文本，例「<NAME_001>报告模拟卡<CARD_001>存在一笔疑似未授权交易」
approved_rule_contextD3规则编号 + 摘要，不含完整规则文本
allowed_outputD3限定模型可返回的字段名，白名单机制
expires_atD3有效期，过期拒收（防重放）

07数据分级与出域判定

分级不是为了分类好看，而是为了把"能不能出域"变成一条可执行、可审计的判定规则。四级的划分依据是"重识别风险"，不是"字段是否被替换过"。

级别数据示例默认策略出域判定
D0
原始敏感		 姓名、证件号、手机号、银行卡号、账号、精确客户标识、令牌映射表 只在内网 禁止。无例外路径，不存在"特批出域"通道
D1
可关联明细		 具体交易时间、金额、商户、地理位置、个案描述等组合后可识别客户的信息 默认内网 需逐案审批：数据负责人审批 + 充分最小化后才可评估
D2
脱敏上下文		 令牌化客户标识、泛化金额/时间、压缩后的咨询意图、无直接身份信息的摘要 可申请外发 可出域：须逐类评估重识别风险、用途、保留期、供应商处理条款
D3
通用/合成		 公开或已批准的通用流程、虚构案例、合成测试集、聚合统计 批准范围内可用 可用：用于外网 Agent 开发、测试、办公产物生成
一个必须写进文档的判断

"脱敏"不必然等于"匿名化"。只要内网仍保留映射表，或者存在可关联字段、外部辅助数据，脱敏数据就仍然可能被重新识别，因此仍具敏感性。出域审批必须按重识别风险判断，不能只凭"字段被替换了"就认定可出域。这条判断决定了审批流程的严格程度，也决定了系统必须记录"这次外发了什么级别、依据哪条审批"。

聚合数据的反推风险

任务书在 MCP 工具里设了 get_aggregate_metrics，这个工具的风险容易被低估：小样本聚合可以反推个人。实现上必须强制最小样本阈值（建议 ≥ 20），并对同一调用方在时间窗内的查询组合做累积风险检测——三次看似无害的切片，合起来可能定位到一个人。

Fail-closed 的具体含义

很多方案在文档里写"安全失败"，但代码里写的是 except: pass。本方案把 fail-closed 落成三条可测试的断言：

断言 1：校验失败即断裂

  • 任一校验环节抛异常，状态强制进入 BLOCKED 或 REJECTED
  • 不存在"降级到宽松模式"的分支
  • 测试方式：注入畸形响应，断言不产生工单

断言 2：边界不可绕过

  • 外发请求只能由跨域网关构造，业务代码无法直接发包
  • 网关不可用时请求排队或失败关闭，绝不直连外网
  • 测试方式：停掉网关，断言无外联流量

MCP 的定位必须说清：它只解决"Agent 怎么调工具"，不提供网络隔离、身份认证或数据授权。把它当成安全机制是这类方案最常见的误判。

明确不提供的工具

以下能力不存在于工具注册表，而不是"存在但拒绝调用"。这个区别很重要：注册表里没有，就不存在配置失误导致误开放的可能。

禁止能力原因

MCP 调用链

WorkBuddy Connector → DMZ MCP Gateway → 内网 MCP Facade → 内部业务 API

每一跳都有独立职责：Connector 持凭证，Gateway 做认证与限流，Facade 做工具到业务 API 的映射与参数校验，业务 API 做最终的数据权限判断。把授权判断放在 Gateway 是不够的——Gateway 只知道"这个角色能不能调这个工具"，不知道"这个客户是否属于这个工号"。

11关键设计决策 ADR

每条决策都记录了"选了什么、为什么、放弃了什么"。这一节是给后来者（以及换人接手时的接手人）看的——比结论更重要的是被否决的选项。

ADR-01三进程物理分离，每区独立数据库

内网、DMZ、外网各自独立进程与独立 SQLite 文件，外网服务代码中不存在访问内网库的连接串。

理由：靠代码规范"不要查客户库"是不可验证的约束；靠进程与网络隔离是可验证的。测试可以直接断言"外网容器到内网库的 TCP 连接被拒绝"。
放弃：单体应用加逻辑分层的简单实现——它无法通过 T12 网络隔离测试。

ADR-02脱敏是独立确定性服务，不与 Agent 同进程

隐私服务只做规则/正则/词典匹配与令牌化，不调用任何模型。

理由：把脱敏交给生成式模型等于把安全控制权交给一个会被提示注入影响的组件。斯坦福案例里这一步也是确定性清洗，不是"让 AI 判断哪些是 PII"。
放弃："让大模型顺便脱敏"——省一个服务，但 T01/T02/T11 全部无法保证。

ADR-03Agent 与模型连接器分离，双 Mock 可独立替换

牛马仕适配器与模型 Connector 是两个独立可替换组件，各有 Mock 实现。

理由：任务书明确"不能把两者合并成一个模型 Mock"。分离后可以证明"换模型不改 Agent、换 Agent 不改网络"，这是验收项之一。
放弃：单层封装——演示更快，但无法展示分层价值。

ADR-04裁决权唯一归属内网规则引擎

模型输出的 recommended_next_step 只是候选，最终路由由 rules/evaluate 决定。

理由：合规要求"Agent 与模型不做最终裁决"。实现上必须让规则引擎在模型之后运行，而不是校验模型的结论。
放弃："高置信度直接回复"——看似体验更好，实则 T10 规则冲突测试必然失败。

ADR-05出域双闸：Schema 白名单 + 残留扫描

第一道只允许声明过的字段通过；第二道对序列化后的完整载荷做原值/实体扫描。

理由：单靠白名单会被"白名单字段里塞了敏感值"绕过（例如 sanitized_context 里混入真名）。两道闸的失效模式不同，可以互补。
放弃：只做正则扫描——误报率高且无法防止新增字段。

ADR-06复原需三元匹配 + 会话绑定，跨会话一次性阻断

request_id、session_id、当前员工身份三者同时匹配才允许回填；同一操作者重复查看幂等，任一维度不符即永久阻断。

理由：T05（request_id 不一致）与 T06（跨会话恢复）是本项目最容易出问题的两个用例。三元匹配把"猜中一个标识符"的攻击面扩大到需要同时伪造三个且身份合法。
放弃：仅凭 request_id 复原——实现简单，但 T06 直接失败。

ADR-07全链路指纹：request_id + trace_id + 版本三元组

每个事件同时记录 Agent 版本、模型供应商/版本、规则版本。

理由：没有版本指纹，出错时无法判断"是模型换版本导致的，还是规则改错了"。这是事故复盘的唯一抓手。
放弃：只记 request_id——日志好看，但不可归因。

ADR-08审计只记元数据，不记明文

审计表记录字段类别、令牌、规则编号、耗时、结果，不记录明文姓名/卡号/金额。

理由：审计日志本身是新的一等敏感数据源。如果日志里有明文，前面所有脱敏都白做。
放弃："记录完整请求便于排查"——排查方便，但日志库变成最大的泄露面。

ADR-09幂等键 = request_id，网关与内外网双层校验

同一 request_id 重复提交只处理一次，重复请求返回首次结果。

理由：T19 重放攻击测试要求"不重复创建业务动作"。跨域调用天然会重试，没有幂等就会重复建单。
放弃：仅在入口去重——网关重试会绕过入口。

ADR-10跨域网关不可用时失败关闭，不做直连降级

网关故障时请求排队或失败，业务代码无"绕过网关直连外网"的分支。

理由：T20 明确要求"不绕过网关直连外网"。架构上只要存在这条降级路径，它就一定会在某次线上故障中被触发。
放弃：可用性优先的自动降级——短期指标好看，长期是合规事故。

ADR-11身份权威只在内网；会话可吊销优先于无状态令牌

登录、角色、锁定、会话全部由内网完成，DMZ 与外网不设账号。令牌只携带会话编号，状态在 sessions 表中，因此停用账号、重置密码、单会话互踢都能立即生效。

理由：无状态 JWT 的最大卖点（免查库）恰好是合规场景的弱点——"吊销立即生效"做不到，离职坐席的令牌要活到过期。辅助控制：PBKDF2-200k 口令派生、失败 5 次锁 300 秒、失败提示与未知账号一致（防枚举）、登录失败响应统一 401 而入口不匹配为 403、设备绑定与登录网段白名单作为可选开关。
放弃：JWT 化——换来的是每次请求多一次本地库查询，SQLite 场景下成本可忽略。

ADR-12账号只能由管理员发放，没有公开注册

管理端提供创建账号与重置密码；角色决定入口（agent→坐席端，其余→管理端），入口不匹配在登录环节就拒绝。

理由："隐藏菜单不是访问控制"。坐席端与管理端是两个物理入口，越权尝试（含冒用他人 emp_id 提交）全部落 AUTHZ_DENIED 审计。分发流程是线下信任链的一部分：口令经私下渠道告知，不进日志、不进报文。
放弃：自助注册与自助改密——在银行语境里，账号生命周期必须有人担责。
